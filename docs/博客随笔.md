### 2. 团队项目的具体规划及描述

我们做的是一个 Web 应用「**智行 · 出行规划智能体**」。

用户用一句自然语言说出出行需求，比如：

> 11 月 12 号从广州去长沙玩 3 天，预算 1500，想逛博物馆和吃辣

系统会自己判断该干什么，然后**真的去调接口**：

1. 先算路线：`route.plan_route` 查 OSRM 实时路网，广州 → 长沙 671 公里、驾车约 7 小时 26 分；
2. 再排行程：`itinerary.build_plan` 读未来天气，发现 11 月 13 日有小雨，把这天下午的户外点位换成室内；
3. 最后算钱：门票 92 + 餐饮 405 + 住宿 520 = 1017 元，对比预算 1500，给出「够用」的结论。

**和「套壳聊天框」的区别**：通用大模型不知道明天的真实天气，也不知道两地真实里程，
所以它给的行程不可执行。我们把**工具调用**做成了产品的骨架 ——
天气、路线、行程三个工具都是真实数据源（open-meteo 与 OSRM，均免密钥），
大模型只是可选的「理解层」，装不装都能完整跑起来。

**进度说明（重要）**：这篇博客不只停在文档阶段，核心功能已经实现并通过 **43 项自动化验收**。
老师/助教现在就可以打开链接，用 `demo / demo1234` 登录体验。

## 二、选题报告

### 1. 选题来自真实调研

组内 4 人 + 同学 18 人，问了三个问题：

| 问题 | 结果 |
|---|---|
| 上次短途出行（1-3 天）前用几个工具查信息 | 平均 **3.7 个**（地图、天气、小红书/大众点评、记账） |
| 从「想去」到「排好日程」花了多久 | 平均 **1.5 小时**，最长 4 小时 |
| 排好的行程实际执行时改过吗 | 22 人里 **17 人改过**，主因「下雨」和「车程估错」 |

三个最集中的抱怨：

1. **攻略是给别人看的，不是给我排的** —— 笔记式内容要人来二次加工；
2. **查天气和查路线是两个 App** —— 信息孤岛；
3. **AI 给的行程一看就是编的** —— 大模型不知道实时信息，用户不敢信。

### 2. 现有方案的不足

| 方案 | 能做什么 | 缺什么 |
|---|---|---|
| 地图 App（高德/百度） | 路线准确 | 不排日程、不管兴趣与预算 |
| 攻略社区（小红书等） | 内容多 | 需人工取舍、不实时 |
| 通用大模型 | 会聊天、会写 | 不知道实时天气与真实里程，容易编 |
| 旅游 OTA | 能订 | 以交易为导向，不做轻量规划 |

**空白点**：没有一个工具把「实时数据 + 排程 + 可核对」合在一起。

### 3. 我们的杀手级功能

1. **一句话触发多工具编排**：一次提问 → 两次工具调用 → 一份可执行行程；
2. **天气驱动改行程**：那天下雨就换成室内；室内排完了**如实说排不下**，不假装；
3. **思考过程可核对**：每一步的工具名、参数 JSON、耗时、返回摘要全部可见
   —— 这是对「AI 编答案」的正面回应，也是我们和套壳产品最大的区别。

【图3：思考过程面板 —— 两次工具调用、参数、耗时都在】

### 4. 技术方案

| 层 | 选型 | 为什么 |
|---|---|---|
| 前端 | 原生 HTML/CSS/JS，无构建 | 答辩机房、手机、离线都能开 |
| 后端 | Python 标准库 `ThreadingHTTPServer` | **零依赖**，`python3 server.py` 即启动；机房 pip 常装不上 |
| 工具层 | 自实现 MCP（JSON-RPC 2.0） | 作业要求「智能体嵌入自研系统」；走标准协议，工具还能被外部客户端复用 |
| 数据 | SQLite 单文件 | 免安装，随项目走 |
| 外部服务 | open-meteo（天气/地名）、OSRM（路网） | 免密钥、真实数据 |
| 理解层 | 规则引擎 + 可选大模型（OpenAI 兼容） | 无 Key 也能完整演示；有 Key 走 LLM 抽 JSON |

## 三、需求分析

需求文档参考 GB/T 8567-2006《计算机软件文档编制规范》中的 SRS 结构编写，
完整版在仓库里：[docs/需求规格说明书.md](https://github.com/zayuchips/zhixing-travel-agent/blob/main/docs/需求规格说明书.md)

结构包含作业要求的全部六项：

| 要求项 | 我们的内容 |
|---|---|
| **迭代记录表格** | 8 个版本（V0.1 → V1.0），逐条写「改了什么 / 谁改 / 为什么改」 |
| **项目标志** | 项目名称与标语、简介、目标用户（学生 / 周末出行者 / 验收方）、运行环境、潜在风险 |
| **思维导图** | 用户角色 / 前端 / 后端 / MCP 工具 / 外部依赖 / 异常处理 / 数据 七大分支，Mermaid 源码 + 文字版 |
| **类图** | `Agent`、`NLU`、`Registry`、`Tool`（四个工具子类）、`Provider`（两个实现）、`Database`，含调用与继承关系 |
| **功能描述** | 24 条功能需求（FR-01 ~ FR-24），**每条都写前置条件、输入、处理逻辑、输出、异常**；前端 12 条、后端 8 条、工具层 4 条 |
| **验收标准** | 24 条验收标准（AC-01 ~ AC-24），每条都能被 `tests/acceptance.py` 或手工一步验证 |

另外补了作业没要求但答辩会问的部分：非功能需求 14 条（性能/安全/可部署性/可维护性）、
数据模型、接口清单、**「9 范围外与已知局限」**（明确写出 POI 只覆盖 9 城、
规则理解层会漏抽、步行耗时是估算等）。我们宁可写清楚做不到的部分，也不在文档里画大饼。
